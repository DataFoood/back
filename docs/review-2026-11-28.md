# Revisão do produto — 28/11/2026

## Problemas e implementação

- A atualização foi integrada à main atual, preservando o fluxo conversacional
  existente, o cupom e a importação com substituição controlada. O novo fluxo
  do catálogo é habilitado com `CHAT_CATALOG_MODE=True`; sem a variável, o
  servidor mantém o comportamento anterior. A redação reutiliza o prompt e o
  cliente Ollama já existentes.
- O chat mantém filtros, exclusões de cozinha, cidade, delivery e orçamento
  baseado em preço de prato. Mostra três prévias e entrega os demais cards sob
  demanda, limitados a 50, com contagem total separada. Surpresa varia a lista
  respeitando os filtros atuais. O PRO usa afinidades e favoritos somente com
  consentimento, sem transformar preferências em filtros obrigatórios.
- A geração é opcional. O catálogo e as respostas de recuperação funcionam
  sem o Ollama. O modelo não cria os IDs retornados. A redação gerada continua
  precisando de avaliação com modelo real; uma validação de nomes não prova
  todas as afirmações que um modelo possa produzir.
- Inferência ocorre antes da transação; gravação detecta mudanças concorrentes
  e responde 409 sem sobrescrever o turno da outra aba.
- Encerramento lógico de conta remove avaliações públicas e sinais pessoais;
  exclusão física usa CASCADE nas avaliações. As notas são recalculadas.
  A migração 0014 remove avaliações de contas já encerradas.
- A API usa uma foto da galeria quando não há capa explícita. Fotos podem
  carregar página de origem, atribuição e licença. Metadados brutos selecionados
  fornecem horários e atendimento sem inventar informações estruturadas.
- O catálogo real está em [[../catalog/README|catalog/README.md]]: 49 registros
  OSM e 152 turísticos; a carga de verificação resultou em 194 cadastros, 151
  com capa e 185 com endereço. Seis registros exigem revisão de possível
  duplicação. A segunda carga foi idempotente.
- Cadastro simplificado: até 3 cozinhas, 2 ambientes e 1 faixa de preço. As
  classificações operacionais antigas continuam no banco por compatibilidade,
  e deixam de ocupar o formulário e o catálogo de opções público.

## Ativar em um ambiente existente

Para a VPS registrada, seguir [[update-vps-2026-11-28]]: backup, atualização
somente de API/workers, migrações e carga sem recriar frontend ou proxy.
Definir `CHAT_CATALOG_MODE=True` no arquivo de ambiente usado pela API.

```bash
uv run python dtfd/manage.py migrate
uv run python dtfd/manage.py load_catalog
uv run python dtfd/manage.py reindex_restaurants
```

Reiniciar API, workers e front com o código atualizado. A imagem do backend
passa a incluir os snapshots em `catalog/`. Não há mudança de dependências.
As novas migrações são 0013 (créditos de imagens e CASCADE), 0014 (limpeza de
avaliações antigas) e 0015 (origem do diretório turístico).

`CHAT_GENERATION_ENABLED=True` e `CHAT_MODEL=qwen3:0.6b` habilitam a redação
local, usando `OLLAMA_URL`. O modelo precisa estar disponível no Ollama.
`CONVERSATION_MODEL` opcional habilita extração adicional de cidade/texto/delivery.
Ausente, a interpretação de pedidos comuns usa o vocabulário local do catálogo.

O resgate de demonstração usa somente o hash SHA-256 configurado em
`PREMIUM_TEST_COUPON_SHA256`. Não há cupom real embutido no código. O resgate
altera apenas `level`, preservando consentimento e papel. Para gerar um hash
sem expor o código no histórico do terminal:

```bash
python -c 'import getpass,hashlib; print(hashlib.sha256(getpass.getpass("Cupom: ").strip().encode()).hexdigest())'
```

`FRONTEND_PROXY_SECRET` na API corresponde a `API_PROXY_SECRET` no front e
habilita o encaminhamento autenticado do IP para os limites por usuário/IP.
Sem o segredo, a API ignora os cabeçalhos específicos do proxy.

## Verificação

Banco PostgreSQL local separado: `datafood_review_20261128`; cache em memória
apenas no processo de verificação. Nenhum banco configurado no `.env` do usuário
foi alterado. As migrações foram aplicadas nesse banco e a carga executada duas
vezes para conferir repetição sem criação de novos cadastros.

Testes Django incluem filtros e contexto, surpresa, PRO/consentimento, orçamento,
isolamento entre contas, cupom, exclusão de avaliações, fallback de capa,
procedência, idempotência, proteção de filiais e bloqueio de URLs internas no
enriquecimento. OpenAPI e consistência de migrações também são verificados.

No front: lint, TypeScript, testes de configuração, build e testes de navegação
com Playwright. Cenários de chat cobrem 320, 390 e 1440 pixels, prévia, popup,
swipe/teclado, sequência sem pular cards, falha e nova tentativa de salvar,
fechar/reabrir, foco, rascunho e seleção por conversa. Home e rodapé têm ensaio
próprio, incluindo redução de movimento.

Resultados: 318 testes na suíte geral Django, 34 verificações na execução
adicional de conversa/segurança e 11 testes de ranking/deploy passaram.
No front, 75 verificações de chat, 16 de cupom e 12 de home/rodapé passaram,
assim como 6 testes de configuração, lint, TypeScript e build com Node 22.23.5.
O build usou uma origem HTTPS reservada de teste e não foi publicado.
A integração real pelo proxy Next → Django confirmou catálogo, contexto,
seleção com imagens e gravação de favorito em banco isolado.
Os testes de navegador controlados não validam a qualidade de um modelo real,
e dados externos ainda precisam de revisão com os estabelecimentos. Esta
entrega não publicou aplicações, não enviou campanhas e não habilitou cobrança.
